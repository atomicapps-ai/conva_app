## React JavaScript and TypeScript fundamentals

- **Q: How do you structure a modern React application?** A: I organize by product capability or feature, with components, hooks, tests, and data access close to the feature. I keep presentational rendering separate from server-state and workflow orchestration, define typed boundaries, and avoid a global store for state that can remain local. Shared UI primitives should encode accessibility and visual consistency; shared domain logic should be framework-independent where possible. The architecture should make the common change easy without hiding data flow.

- **Q: When should state be local, contextual, or global?** A: Local state is the default when one component subtree owns it. Context is appropriate for relatively stable cross-cutting values such as theme, authentication, or a scoped service, but high-frequency updates can cause broad re-renders. A global store is useful when many distant features need coordinated, mutable client state. Remote server state should usually be handled by a data-fetching cache rather than copied into a general client store. The decision depends on ownership, update frequency, persistence, and debugging needs.

- **Q: What causes a React component to re-render?** A: A component re-renders when its state changes, its parent renders, a consumed context value changes, or an external-store subscription reports a change. Rendering is not the same as committing DOM changes; React reconciles the new output against the previous tree. I optimize only measured problems, stabilize identities where they actually matter, keep state close to its consumers, split expensive subtrees, and avoid creating effects that continually update state.

- **Q: Explain useEffect and common mistakes.** A: `useEffect` synchronizes a component with an external system such as a subscription, browser API, timer, or imperative widget. It is not the default tool for deriving one piece of state from another. Common mistakes are missing dependencies, stale closures, no cleanup, fetch races, and effect loops caused by unstable objects or callbacks. I prefer deriving during render, handling user-caused work in event handlers, and using framework or data-library primitives for fetching. When an effect is necessary, cleanup and cancellation are part of the design.

- **Q: How do you prevent stale state bugs?** A: I remember that each render captures a snapshot of props and state. When the next value depends on the previous value, I use a functional state update. For async work I use cancellation or request identity to prevent an older response from overwriting newer state. I also avoid storing redundant derived state and keep effect dependency lists accurate.

- **Q: What is React keying and why does it matter?** A: Keys identify siblings across renders so React can preserve or reset component identity correctly. Stable domain identifiers are better than array indexes when items can be inserted, removed, or reordered. A changed key intentionally remounts the component and resets its state; an unstable key causes accidental state loss and extra work.

- **Q: How do you improve React performance?** A: I start with user-facing measurements and the React profiler. Typical fixes include moving state closer to where it is used, virtualizing large lists, avoiding unnecessary context churn, splitting code by route or capability, using server-state caching, and memoizing only expensive computations or identity-sensitive props. I also optimize network waterfalls, bundle size, images, and rendering frequency because React CPU time is only one part of perceived performance.

- **Q: How do you design accessible React components?** A: I start with semantic HTML, keyboard access, visible focus, labeled controls, sensible heading structure, and correct status or error announcements. I use ARIA only when native semantics are insufficient, manage focus intentionally for dialogs and dynamic workflows, and test with keyboard navigation plus automated accessibility checks. Accessibility belongs in shared primitives and acceptance criteria, not as a final audit.

- **Q: What TypeScript practices matter most in a full-stack codebase?** A: Enable strict checking, model domain states with discriminated unions, validate untrusted data at runtime, and generate or share types from contracts where practical. Avoid `any`; use `unknown` at boundaries and narrow it. Keep optional fields meaningful, use branded or opaque identifiers when mix-ups are dangerous, and make impossible states difficult to represent. Types improve change safety, but runtime validation is still required at network, storage, and user-input boundaries.

- **Q: Explain JavaScript event loop behavior.** A: JavaScript runs synchronous code on a call stack. Promise continuations use the microtask queue, while timers and I/O callbacks are scheduled through task queues by the host environment. Microtasks run before the next task, so an unbounded microtask chain can starve timers or rendering. In Node, blocking CPU work on the event loop delays every request, so CPU-heavy work should be bounded, moved to worker threads or another service, or processed asynchronously.

- **Q: What is the difference between debounce and throttle?** A: Debounce waits for a quiet period before running, which is useful for search input or autosave. Throttle limits execution to at most once per interval, which is useful for scroll, resize, or telemetry. I choose based on the product behavior, include leading or trailing semantics deliberately, and handle cancellation on unmount.

## Node API and GraphQL fundamentals

- **Q: Why is Node.js a good fit for APIs, and where is it not?** A: Node is strong for I/O-heavy services because one event loop can coordinate many concurrent operations with a relatively small footprint, and TypeScript can unify language and types across the stack. It is a poor fit for unbounded CPU-heavy work on the main event loop. For CPU-intensive tasks I use worker threads, a job queue, a specialized service, or a different runtime while keeping the API boundary consistent.

- **Q: How do you prevent blocking the Node event loop?** A: Avoid synchronous filesystem, crypto, compression, or parsing work in request paths; bound input sizes; stream large payloads; paginate responses; use database timeouts; and measure event-loop lag. Some Node APIs use the libuv worker pool, so huge jobs can starve that pool even when the JavaScript thread is free. CPU-heavy work belongs in workers or asynchronous background processing.

- **Q: How do you design a production Node service?** A: I separate transport, application use cases, domain rules, and infrastructure adapters. I validate input at the boundary, propagate a correlation ID, apply authentication and authorization explicitly, centralize typed error mapping, set deadlines on downstream calls, emit structured logs and metrics, and expose health and readiness checks. I support graceful shutdown so deployments stop accepting new traffic, complete or abandon work safely, and close resources.

- **Q: How do you handle errors in an API?** A: I distinguish validation, authentication, authorization, not-found, conflict, rate-limit, dependency, and internal errors. Clients receive a stable, safe error shape with a trace or correlation ID; internal logs retain diagnostic context without leaking secrets or sensitive data. Retries are reserved for transient and idempotent operations, with exponential backoff and jitter. Operational metrics group errors by route, dependency, and cause.

- **Q: REST or GraphQL?** A: REST is simple, cache-friendly, and a good fit for resource-oriented APIs and public integrations. GraphQL is valuable when clients need flexible traversal across related data, multiple frontends have different data needs, or schema evolution and strong tooling matter. GraphQL moves complexity to the server: resolver performance, authorization at fields and objects, query cost, caching, and N+1 loading. I choose based on client diversity, data graph, operational needs, and team capability rather than fashion.

- **Q: How do you prevent the GraphQL N+1 problem?** A: Batch and cache related loads within the scope of a request, commonly with a DataLoader-style abstraction. Resolvers request individual keys, and the loader combines them into one set-based database or service call while preserving key order. Request-scoped caching prevents data leakage across users. I also inspect resolver traces and query plans because not every N+1 should be hidden by a generic loader if the better fix is a join or purpose-built read model.

- **Q: How do you secure a GraphQL API?** A: Authenticate once at the edge, then authorize at the domain operation and field or object level where needed. Use allowlisted operations for trusted clients when practical, depth and complexity limits, pagination caps, rate limits, timeouts, input validation, and safe error responses. Disable unrestricted introspection in production only if the operational tradeoff is understood; it is not a substitute for authorization. Monitor resolver latency and rejected query cost.

- **Q: How do you evolve a GraphQL schema?** A: Prefer additive changes, mark fields deprecated with a replacement and reason, measure actual field usage, and remove only after consumers migrate. Avoid changing nullability or meaning in place. Use schema checks in CI, contract tests for important clients, and ownership metadata for domains. The schema is a product contract, not just generated types.

- **Q: Cursor or offset pagination?** A: Offset pagination is simple and supports page numbers, but it becomes expensive at large offsets and can duplicate or skip records when concurrent writes reorder results. Cursor pagination uses a stable, deterministic sort key—often a composite such as creation time plus ID—and scales better for changing datasets. I use opaque cursors, consistent sort direction, explicit page-size limits, and indexes that match the cursor predicate.

- **Q: What does backpressure mean?** A: Backpressure is how a producer is slowed or buffered when a consumer cannot keep up. In Node streams, consumers signal whether writes can continue and producers wait for drain rather than accumulating unlimited memory. In distributed systems, queues, bounded concurrency, rate limits, and load shedding serve similar purposes. The goal is stable degradation instead of memory growth or cascading failure.

## PostgreSQL data modeling and distributed data fundamentals

- **Q: How do you design an entity-relationship model?** A: Start with business concepts, ownership, invariants, and cardinality before tables. Identify aggregate boundaries and lifecycle rules, normalize data to remove update anomalies, then denormalize selectively for measured read needs. Use primary keys, foreign keys, unique constraints, checks, and appropriate nullability to make the database enforce valid states. Model many-to-many relationships explicitly, name relationships clearly, and design indexes from real access patterns.

- **Q: When would you normalize versus denormalize?** A: Normalize the source-of-truth transactional model to protect consistency and make updates understandable. Denormalize when a proven read pattern, reporting workload, or distributed boundary justifies duplication. Once data is duplicated, define the owner, update mechanism, acceptable staleness, reconciliation path, and failure handling. A search index or materialized projection is often safer than weakening the transactional model for every query.

- **Q: Explain PostgreSQL MVCC.** A: PostgreSQL uses multiversion concurrency control so each statement or transaction sees a consistent snapshot while readers and writers generally avoid blocking each other. Updates create new row versions; old versions remain until vacuum can reclaim them. MVCC improves concurrency but creates operational concerns such as long-running transactions, dead tuples, vacuum health, transaction-ID wraparound, and the need to choose isolation deliberately.

- **Q: What transaction isolation level would you use?** A: `READ COMMITTED` is a practical default when each statement may see newly committed data and the application can tolerate that. `REPEATABLE READ` gives a stable transaction snapshot but can require retrying serialization-style conflicts. `SERIALIZABLE` provides the strongest behavior through conflict detection and requires a retry strategy. I choose the weakest level that preserves the business invariant, and for contested writes I may use row locks, optimistic version columns, or atomic conditional updates.

- **Q: How do you diagnose a slow PostgreSQL query?** A: Capture the exact query and parameters, use `EXPLAIN (ANALYZE, BUFFERS)` in a safe production-like environment, and compare estimated versus actual rows. Look for sequential scans, bad join order, repeated loops, sorts spilling to disk, lock waits, and I/O. Check statistics, index selectivity, predicate shape, implicit casts, N+1 behavior, connection pressure, and data skew. Fix the verified bottleneck, then validate latency, throughput, and write overhead on representative data.

- **Q: How do you choose an index?** A: Match it to the predicate, join, and ordering patterns. B-tree is the default for equality, ranges, and ordering; GIN is useful for `jsonb`, arrays, and full-text-style membership; BRIN can be efficient for very large physically correlated tables. Composite index column order follows the most useful leading predicates and sort needs. Partial and covering indexes can be powerful. Every index increases storage and write cost, so I validate usage and remove redundant indexes.

- **Q: When would you use jsonb?** A: `jsonb` is useful for sparse or evolving attributes, external payloads, and data whose structure varies but still benefits from PostgreSQL transactions and indexing. I keep frequently filtered, joined, constrained, or aggregated fields in typed columns. For `jsonb` queries I use appropriate GIN or expression indexes and validate operator support. I avoid turning the whole relational model into an unvalidated blob.

- **Q: When should a PostgreSQL table be partitioned?** A: Partitioning is primarily a data-management and pruning tool for very large tables with a clear partition key, such as time or tenant. It can simplify retention and improve queries that filter on the key, but it adds operational and constraint complexity and does not replace good indexing. I verify that queries actually prune partitions and that uniqueness requirements can include the partition key.

- **Q: SQL versus NoSQL?** A: I choose from consistency, access patterns, relationship complexity, scale, latency, and operational ownership. Relational databases are strong when transactions, constraints, joins, and evolving questions matter. Key-value or document stores are strong when access patterns are known, horizontal scale and predictable latency dominate, and aggregate boundaries are clear. It is common to use PostgreSQL as the system of record, Redis as a cache, and OpenSearch as a query projection—but every extra store creates consistency and operational work.

- **Q: How do you maintain consistency across services?** A: Avoid distributed two-phase commit unless the environment truly supports and requires it. Give each service ownership of its data, commit the local transaction, and publish an event reliably using an outbox pattern. Consumers must be idempotent, track processed message IDs or enforce natural uniqueness, and support retries and dead-letter handling. Multi-step business workflows can use sagas with explicit compensating actions and observable state.

- **Q: What is the outbox pattern?** A: Write the business change and an outbound event record in the same local database transaction. A relay later publishes the event to the broker and marks or records progress. This prevents the dual-write failure where data commits but event publication fails, or vice versa. Publication may still be at least once, so consumers must be idempotent.

- **Q: What is optimistic concurrency control?** A: Store a version or timestamp with the record and include the expected version in the update predicate. If zero rows update, another writer changed the record and the application can reload, merge, or return a conflict. It avoids holding locks across user think time and works well when conflicts are uncommon. The product still needs a clear resolution experience.

## Cloud distributed systems and reliability

- **Q: How do you design an event-driven workflow for at-least-once delivery?** A: Assume duplicates and occasional reordering. Give each event a stable identifier and schema version, make consumer side effects idempotent, commit progress atomically where possible, and use bounded retries with exponential backoff and jitter. Configure a DLQ for poison messages, expose queue age and depth, and provide a replay process. If order matters, partition by the business key or use FIFO/session semantics rather than demanding global ordering.

- **Q: SNS, SQS, Kinesis, or Kafka?** A: SQS is a durable work queue and load-leveling buffer; SNS is push-style fan-out to multiple subscribers; Kinesis and Kafka are ordered append-only streams suited to replay, consumer groups, and high-throughput event histories. I choose based on whether each message is work for one consumer or an event for many, whether replay is required, ordering scope, throughput, retention, latency, and operational ownership.

- **Q: How do you set an SQS visibility timeout?** A: It must be longer than normal processing time with enough margin, but not so long that failed work is hidden unnecessarily. For variable or long jobs I extend visibility while processing and keep work idempotent in case the lease expires. I align maximum receives with the retry policy and DLQ, monitor age of oldest message and receive counts, and control Lambda concurrency so downstream systems are not overwhelmed.

- **Q: What does idempotency look like in practice?** A: Derive or receive an idempotency key from the business operation, store the key with the result or state transition, and make the check and write atomic. A duplicate returns the previous result or becomes a no-op. For messages, a unique constraint on event ID or business key is often more reliable than an in-memory cache. The retention period for keys must cover the system's realistic retry and replay window.

- **Q: How do you avoid retry storms?** A: Retry only transient failures and only when the operation is safe, cap attempts and total retry budgets, use exponential backoff with jitter, respect `Retry-After`, and pair retries with circuit breakers and timeouts. Load shedding and queues protect dependencies during bursts. Multiple layers should not independently multiply retries without coordination.

- **Q: What is a circuit breaker?** A: It stops repeatedly calling a failing dependency after a threshold, fails fast or uses a fallback while the dependency recovers, and allows limited probes in a half-open state. It is not a replacement for timeouts or retries; it bounds the damage they can cause. Metrics and state transitions must be observable because a badly tuned breaker can hide recovery or create flapping.

- **Q: How do you design observability?** A: Start from service-level objectives and important user journeys. Use structured logs with correlation IDs, metrics for traffic, errors, latency, and saturation, and distributed traces across service boundaries. For queues add depth, age, receive count, consumer lag, DLQ count, and processing duration. Alerts should correspond to customer impact or actionable risk, and runbooks should explain diagnosis and recovery.

- **Q: How would you deploy safely?** A: Use immutable artifacts, infrastructure as code, automated tests and policy checks, environment promotion, and backward-compatible contracts. Prefer rolling, blue-green, or canary deployment based on risk. Separate deployment from release with feature flags when useful, monitor key indicators during rollout, and define automated or one-command rollback. Database changes use expand-and-contract so old and new versions can coexist during the deployment window.

- **Q: AWS or Azure?** A: I have delivered in both. I map needs to capabilities: Lambda or Azure Functions, API Gateway or API Management, SQS/SNS/EventBridge or Service Bus/Event Grid, CloudWatch or Azure Monitor, IAM/Cognito or Entra ID, and CloudFormation/CDK or ARM/Bicep/Terraform. The deeper concerns—identity, network boundaries, idempotency, observability, deployment safety, cost, and data ownership—transfer across providers.

- **Q: How do you control cloud cost?** A: Make cost visible by service, environment, and product capability; right-size compute and databases; use autoscaling and scale-to-zero where appropriate; set retention and lifecycle policies; and reduce unnecessary data transfer, logging volume, and duplicated work. Serverless shifts cost to usage, so I watch invocation patterns, duration, concurrency, retry amplification, and storage access. Cost is a design constraint and an operational metric, not a one-time cleanup.

## Testing troubleshooting and Agile delivery

- **Q: What is your testing strategy for a full-stack feature?** A: I map tests to risk. Pure domain logic gets fast unit tests; database and service adapters get integration tests against realistic dependencies; API and event contracts get schema and consumer-driven checks; and a small set of end-to-end tests covers critical user journeys. I test failure paths, authorization, retries, concurrency, and observability. CI runs the cheapest high-signal tests first and prevents promotion when required gates fail.

- **Q: How do you test GraphQL?** A: Test domain logic separately from transport, then integration-test operations through the GraphQL layer with authentication and a real or representative data adapter. Validate authorization, nullability, error shapes, pagination boundaries, batching behavior, and query-cost controls. Use schema checks to catch breaking changes and a small number of client journeys to validate end-to-end behavior.

- **Q: How do you debug a slow consumer-facing page?** A: Reproduce with representative data and measure the whole path: browser network waterfall, bundle and render timing, API traces, resolver spans, database plans, cache behavior, and downstream latency. Determine whether the problem is download, main-thread work, render churn, over-fetching, N+1 calls, database access, or dependency saturation. Fix the dominant bottleneck, validate user-centric metrics, and add a regression test or alert.

- **Q: How do you troubleshoot an intermittent production issue?** A: Establish scope, customer impact, timeline, and recent changes; correlate logs, metrics, and traces using request or event IDs; compare healthy and failing instances or cohorts; and form one falsifiable hypothesis at a time. Mitigate safely before deep diagnosis if impact is active. Afterward, document the root cause, contributing conditions, detection gap, and prevention work without blaming individuals.

- **Q: What do you contribute in Scrum ceremonies?** A: In refinement I clarify outcomes, acceptance criteria, dependencies, and technical risk. In planning I help slice work to a demonstrable increment and make capacity constraints explicit. Daily, I communicate progress and blockers rather than reciting activity. In review I connect the demo to user value and evidence. In retrospective I propose one or two measurable process experiments and follow up on whether they helped.

- **Q: How do you estimate work?** A: I decompose the vertical slice, identify unknowns and dependencies, compare with recent work, and express uncertainty rather than false precision. For a large unknown I timebox a spike with a concrete decision output. Estimates support prioritization; once work starts, throughput, remaining scope, and newly discovered risk are more useful than defending the original number.

- **Q: What makes a good code review?** A: It protects correctness, security, operability, and maintainability while teaching and preserving momentum. I review the requirement and tests first, then boundaries, failure modes, data consistency, and readability. I distinguish blocking issues from suggestions, explain why a change matters, and prefer small pull requests. Repeated feedback should become tooling, documentation, or a shared abstraction.

- **Q: How do you handle technical debt?** A: Tie debt to a concrete cost or risk: slower delivery, incidents, security exposure, difficult onboarding, or cloud expense. Fix debt opportunistically around changed code, reserve deliberate capacity for high-leverage items, and define measurable completion. I avoid both extremes—ignoring debt until it becomes a rewrite, or polishing internals without product value.
