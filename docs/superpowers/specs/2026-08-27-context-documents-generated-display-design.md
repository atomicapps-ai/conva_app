# Context edit wizard: generated documents — display fix + duplicate root cause

> Brainstorming-skill design doc. Status: **approved** (owner, 2026-08-27).
> Shipping on `claude/conva-app-ui-modernization-igllsd`. Two parts landing
> together: Part A (below) was the original scope; Part B was folded in
> after the owner reported apparent duplicate generated documents while
> testing Part A's problem statement.

## Part A — Distinguish generated documents in the Documents list

### Problem

`SimConSetup.tsx` step 2's "Documents" section lists **every** document in
the whole library (`backend.rag.list()`, unscoped) as a checkbox bound to
`selected`/`source_doc_ids` — "attach this to ground the context." Ally's
own generated documents (Context knowledge, Research findings, Interview
Q&A — `RagDocument.source === "generated"`) are ordinary `RagDocument`s in
the same store, so they show up in this same checkbox list too, unchecked,
indistinguishable from a regular attachable file.

This is misleading on two counts: (1) generated documents are already
always part of the context's grounding via the knowledge profile's
`doc_ids` — they don't need (and toggling their checkbox doesn't actually
control) attachment the way `source_doc_ids` does for ordinary docs; (2)
the list is entirely unscoped, so a generated document belonging to a
**different** context shows up here too, offering to "attach" material
that has nothing to do with the context being edited. There's also no way
to view a generated document's content or trigger regeneration from this
screen — the owner has to leave the edit flow and go to the context's
detail page.

### Design

Split the Documents section into two parts. The existing checkbox list
becomes **"Attached documents"** and excludes every generated document
(all of them, regardless of context — generated docs are never manually
attached/detached by checkbox). A new **"Generated by Ally"** subsection
(shown only when editing an existing context, i.e. `initial` is set —
nothing can be generated yet during creation) lists only the generated
documents that belong to *this* context (`d.context_ids.includes(initial.id)`);
documents generated for other contexts are filtered out of the screen
entirely, not just out of the checkbox list.

Each row in the new subsection reuses the existing "By conva" visual
language already established in `LibraryPane.tsx` (sparkle icon, `text-ai`
tint, the `conva` pill badge) for consistency — no new visual vocabulary.
No checkbox: instead, a **View** toggle expands the document's text inline
via `backend.rag.documentText(id)`, the same lazy-fetch-on-toggle pattern
`SimConDetail.tsx` already uses for its three document rows. A
**"Regenerate resources"** button sits at the top of the subsection,
calling `backend.simcon.generateDossier(initial.id)` with a busy state
("Regenerating…"), then re-fetching `backend.rag.list()` so any
content/id changes (a doc replaced on regenerate) show immediately —
matching `SimConDetail`'s existing regenerate semantics exactly, just
reachable from the edit wizard too.

### Files (Part A)

- `src/components/simcon/documentSplit.ts` (new) — pure helper
  `splitDocuments(docs: RagDocument[], contextId: string | undefined):
  { attachable: RagDocument[]; generated: RagDocument[] }`. A document is
  `generated` when `source === "generated"` AND `context_ids` includes
  `contextId`; a non-generated document (any other `source`) is always
  `attachable`, regardless of its `context_ids`; a generated document
  belonging to a *different* context (or to none) is excluded from
  **both** lists — per the approved design, it's filtered off this screen
  entirely, not offered as attachable. `contextId` undefined (creation
  mode) → every generated document is excluded (nothing can belong to a
  not-yet-created context) — in practice `docs` fetched at creation time
  won't contain any such document anyway, but the helper is defined to
  handle it explicitly
  rather than relying on that.
- `src/components/simcon/documentSplit.test.ts` (new) — unit coverage.
- `src/components/simcon/SimConSetup.tsx` (modify) — use the helper to
  drive the two lists; add the new "Generated by Ally" subsection + its
  View-toggle state + the Regenerate button.

### Out of scope (Part A)

- Any change to `SimConDetail.tsx`'s own "Ally documents" card (unchanged,
  still the canonical place to view/regenerate outside the edit wizard).
- Any change to how ordinary (non-generated) documents are attached or to
  `source_doc_ids` semantics.
- Scoping the "Attached documents" list itself to anything narrower than
  the whole library (that's the existing, intentional "Path B: pick from
  your library" cross-context reuse behavior — not touched here).

### Testing (Part A)

- `documentSplit.test.ts`: a generated doc tagged to the current context
  → `generated`; a generated doc tagged to a different context → excluded
  from both lists; a generated doc tagged to no context at all → also
  excluded from both (same "not this context's" case); a `file`/`pasted`
  doc → always `attachable` regardless of `context_ids`; `contextId`
  undefined → every generated doc excluded, every non-generated doc still
  `attachable`.
- `SimConSetup.test.tsx`: the "Generated by Ally" subsection doesn't
  render in creation mode (`initial` unset); with `initial` set and a
  generated doc tagged to it present in the docs list, the subsection
  renders the row with no checkbox and a View control; clicking View
  fetches and displays text via a mocked `backend.rag.documentText`.
- Manual QA (owner): edit an interview context that has generated
  documents — the Interview Q&A / Context knowledge / Research findings
  rows appear under "Generated by Ally," badged, no checkbox, View
  expands the text inline; "Regenerate resources" re-runs generation and
  the row's content updates; a generated document from a different
  context does not appear anywhere on this screen.

## Part B — Fix the save-payload field loss that orphans generated documents

### Problem

Root cause of the "two that look like duplicates" the owner observed while
testing Part A's problem area. Replace-on-regenerate is already
implemented server-side — each of the three generation stages in
`simcon_generate_dossier` deletes the document at its tracked id
(`dossier_doc_id`/`research_doc_id`/`qa_doc_id`) before writing the fresh
one, specifically so regenerating never piles up copies. But
`SimConSetup.tsx`'s `finish()` save call omits four `SimConSession` fields
that exist and are `#[serde(default)]` on the Rust side (so a missing
field silently defaults instead of erroring): `research_doc_id`,
`qa_doc_id`, `glossary_definitions`, `resources_stale`. Every time an
existing context is edited and saved through the wizard, these silently
reset (`None`/empty/`false`).

Sequence that produces an orphan: generate resources (`qa_doc_id` =
doc-A) → edit the context, Finish → `qa_doc_id` resets to `None` on save
→ Regenerate → the replace step finds nothing to delete (id is `None`) →
creates doc-B → doc-A is now an orphan, still tagged to this context via
`context_ids`, indistinguishable from doc-B anywhere the doc list is
scoped by context (including Part A's new "Generated by Ally" section,
which filters by `context_ids`, not by the tracked id — it would show
both). The same gap silently breaks cached term definitions
(`glossary_definitions` reset) and the "Stale" pill
(`resources_stale` reset) on every edit-save, independent of regenerate.

### Design

Add the four missing fields to `finish()`'s save payload in
`SimConSetup.tsx`, preserving them from `initial` exactly like the
existing `dossier_doc_id: initial?.dossier_doc_id ?? null` line already
does — the fix is symmetry with a pattern that's already there for one of
the four sibling fields, not new logic. `glossary_definitions` needs a
plain-object default (`{}`) rather than `null`, matching its
`Record<string, string>` mirror type.

No backend change — the delete-old/create-new logic is already correct;
it only needed its inputs to survive a save.

### Files (Part B)

- `src/components/simcon/SimConSetup.tsx` (modify) — `finish()`'s
  `backend.simcon.save({...})` call gains:

  ```ts
  research_doc_id: initial?.research_doc_id ?? null,
  qa_doc_id: initial?.qa_doc_id ?? null,
  glossary_definitions: initial?.glossary_definitions ?? {},
  resources_stale: initial?.resources_stale ?? false,
  ```

  (placed alongside the existing `dossier_doc_id` line, same style).

### Out of scope (Part B)

- Any change to the replace-on-regenerate logic itself (already correct).
- A one-time cleanup/migration for orphaned documents already created by
  this bug on existing installs — the owner can delete stray duplicates
  by hand via the Library pane; not worth automated cleanup tooling for a
  bug this narrow.

### Testing (Part B)

- `SimConSetup.test.tsx`: editing an existing context (`initial` set,
  with `research_doc_id`/`qa_doc_id`/`glossary_definitions`/
  `resources_stale` populated) and saving calls `backend.simcon.save`
  with all four fields preserved from `initial`, not reset to their
  defaults.
- Manual QA (owner): generate resources on an interview context, edit any
  field and Finish, then Regenerate — exactly one Interview Q&A / Context
  knowledge / Research findings document exists afterward (no orphan),
  and a previously-cached term definition still resolves instantly after
  the edit-save (confirms `glossary_definitions` survived too).
